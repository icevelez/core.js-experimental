# Creating an Application

Core provides two ways to bootstrap an application.

1. **Template Loader** (recommended)
2. **Manual Component Mounting** (low-level API)

Both produce the exact same result. The template loader is simply a convenience built on top of the manual API.

---

## Method 1 — Template Loader (Recommended)

For most applications, Core provides a browser-native component loader.

Instead of manually loading and mounting your root component, you declare it directly in HTML.

```html
<!DOCTYPE html>
<html>
<head>
    <title>Core Playground</title>

    <script type="importmap">
    {
        "imports": {
            "core": "https://cdn.jsdelivr.net/gh/icevelez/Core@master/core/runtime.js",
            "core-compiler": "https://cdn.jsdelivr.net/gh/icevelez/Core@master/core/compiler.js"
        }
    }
    </script>

    <script type="module">
        import { init } from "core";

        init();
    </script>
</head>

<body>

<template
    id="app"
    core-src="./src/App.html">
</template>

</body>
</html>
```

This matches the example project structure shown in the playground. 

---

### What `init()` Does

When `init()` is called, Core scans the current document for every template containing the `core-src` attribute.

```html
<template core-src="./src/App.html"></template>
```

Each template is then:

1. Loaded as a Core component
2. Compiled (if necessary)
3. Mounted in place of the template
4. Registered internally so it can later be disposed

Conceptually, the loader performs something similar to:

```js
const App = await component("./src/App.html");
mount(App, template, true);
```

This lets an HTML document describe its own component tree without writing additional bootstrapping code.

---

### Why Use the Template Loader?

The template loader encourages what Core calls a **resource-centric workflow**.

Instead of thinking:

> "Create an application, then mount it."

you think:

> "This HTML document contains components."

Each component is simply another web resource referenced by its URL.

```html
<template core-src="./src/Header.html"></template>

<template core-src="./src/Sidebar.html"></template>

<template core-src="./src/Dashboard.html"></template>
```

This makes applications feel closer to the web platform itself.

---

### Accessing Loaded Components

`init()` returns an application controller.

```js
import { init } from "core";

const app = await init();
```

Loaded components are available through:

```js
app.components
```

which is a `Map` whose values are each component's dispose function.

```js
app.components.get("App.html")();
```

To dispose every loaded component:

```js
app.dispose();
```

Most applications never need to access these APIs directly, but they are available for advanced scenarios such as dynamically disposing portions of UI in an application.

---

# Method 2 — Manual Component Mounting

The template loader is built on top of Core's lower-level component API.

If you need complete control over how components are loaded and mounted, you can use the manual API directly.

## Loading the Root Component

Every Core application starts by loading a root component using `component()`.

```js
import { component } from "core/handlebar";

const App = await component("App.html");
```

This compiles the component and returns a mountable instance. 

---

## Mounting the Application

Applications become visible only after being mounted.

```html
<div id="app"></div>
```

```js
import { component } from "core/handlebar";
import { mount } from "core";

const App = await component("App.html");

mount(App, "#app");
```

The application is rendered inside the target container while leaving the container itself intact. 

---

## Application Scope

Each mounted application maintains its own isolated reactive graph.

* Signals are scoped per application.
* Effects are tracked independently.
* Lifecycle cleanup occurs when the application is disposed.

Multiple Core applications can coexist on the same page without interfering with one another.
